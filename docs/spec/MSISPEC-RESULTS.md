# MSISPEC Appendix C: Windows validation results

Run of the [Appendix C](MSISPEC.md#appendix-c-windows-validation-test-matrix)
test matrix on 2026-10-25. Every case was executed by
[`msitest`](msitest/doc.go), which builds its fixtures through the native
importer and through an independent CFB, cabinet and table implementation
written from MSISPEC.md alone (no WiX, no msitools; only ENV-02, run on
2026-10-29, compares WiX and wixl output). Per-variant evidence is in
[`msitest/results/<case>/<variant>/log.md`](msitest/results); fixtures and
verbose `msiexec` logs are regenerated by running the case again.

Results recorded before 2026-10-28 use the project's former name go-msi and
the `run` DLL's former entry point `GoMsiRun` (now `BuilderRun`, MSISPEC.md
section 17.6); they are left as they ran.

## Findings that change the spec

Contradicted claims:

1. **31 columns, not 32 (MSIDB-07).** `CREATE TABLE` and `ALTER TABLE ADD` reject
   the 32nd column with error 2280, and `MsiDatabaseImportW` rejects a 32-column
   archive with 2216. Section 3 says "at most 32 columns".
2. **x64 Page Count minimum is 150 on this engine (SUM-03).** `x64;1033` with
   Page Count 100–149 fails with 1620; 150, 199 and 200 install. Values above
   500 fail with 1613 for both platforms (the engine is 5.0), and 0 or 1 also
   give 1613. Sections 4 and 8.2 say x64 needs ≥ 200; ICE80 may still require
   200, which was not run.
3. **String refcounts are 15 bits in `msi.dll` (MSIDB-05).** The native writer
   stores refcount mod 32768 (32767 refs → 32767, 65534 → 32766, 70000 → 4464).
   When a string's count is a multiple of 32768 the commit drops the string from
   the pool: every one of 32768 or 65536 rows then reads back as NULL. Reading
   ignores the stored refcount (0, 32768 and 65535 all read fine), but a native
   commit keeps it masked to 15 bits and drops the string when that is 0. Section
   3 said "Fail above 65535" until 2026-10-29; its "refcount MUST equal the
   stored references" holds only up to 32767 for what Windows writes or
   survives. A writer whose output may be edited by `msi.dll` should keep every
   refcount in 1…32767.
4. **`*` does not imply removal (ENVVAR-01).** `=*MSISPEC_PERM` (machine scope,
   no `-`) survives uninstall. Section 8.13 says `*` "also implies removal at
   uninstall"; the other environment claims hold (below).
5. **`RemoveExistingProducts` before `InstallValidate` is accepted (UPG-04).**
   1399 removes the old product like 1401; only 5802 gives 2613.
6. **Native packages are CFB v4 (CFB-01).** `MsiOpenDatabaseW(MSIDBOPEN_CREATE)`
   writes a 4096-byte-sector v4 file even for a 20 KB database; section 2 only
   knew large native packages to be v4. v3 and v4 repacks of the same streams
   behave identically.
7. **Per-user rollback: confirmed only for non-administrators (CA-01).** A
   deferred action that fails after `PublishProduct` rolls back completely in
   an install by an elevated administrator. In a non-administrator's install,
   the rollback of every failure after `RegisterProduct` cannot remove the
   registration (`Info 1403`, access denied): after `PublishProduct` the
   product stays installed (state 5) and a reinstall fails with 1603; between
   `RegisterProduct` and `PublishProduct` an HKLM entry stays (state 2) that
   `msiexec /x` cannot remove (1605). WiX issue 8574 reproduces with a
   package the harness built. Windows Server also refuses
   non-administrator installs by default (`DisableMsi` 1, 1625); see
   [Per-user rollback](#per-user-rollback-ca-01).
8. **SystemIdentifier (SUM-07).** The native writer stores `0x0002000A`, not
   `0x00020006`, and the engine ignores the field: 0, 5, 6 and `0xFFFFFFFF`
   all install.
9. **An existing service is reconfigured, not left alone (SVC-06).** With a
   service of the same name already registered, InstallServices gave it the
   package's binary path and display name and kept a description the package
   did not write. Section 8 reported that such a service is left alone. A
   `ServiceControl` delete at install (event 8) removes it first, so nothing
   of it carries over.
10. **`WindowsBuild` is 9600 on current Windows (PROP-02).** On Windows
   Server 2025 (build 26100) the engine sets `VersionNT` 603 and
   `WindowsBuild` 9600, the values of Windows 8.1, so `WindowsBuild` does not
   tell Windows 10, 11 or Server releases apart as section 19.2 said. A
   registry search of `CurrentBuildNumber` does (section 8.6), and
   msi-builder's warning for version-bounded searches of Windows' own files
   now names it.

Settled unverified items and new facts:

- The root CLSID is checked: a zero, one-byte-changed or transform CLSID gives
  `MsiOpenDatabaseW` 110 and `msiexec` 1620 with Note 2766 (CFB-02).
- `msi.dll` searches the directory tree: swapping the top node's children
  (names no longer ordered) gives 110 / 1620, while colours are ignored
  (all-red, red root and a degenerate right chain all install). Writers MUST
  emit a correctly ordered tree (CFB-04, CFB-06).
- The native writer gives empty streams start sector ENDOFCHAIN; FREESECT and 0
  are also accepted. `MsiRecordReadStream` on a 0-byte stream returns 13
  `ERROR_INVALID_DATA` (CFB-03).
- The long-reference flag is set exactly when the highest string ID reaches
  65535 (65534: 2-byte references, 65535: 3-byte), counting free slots (MSIDB-06).
- The native pool is not sorted and keeps free slots at IDs 1–4; refcounts
  equal the references in all streams including `_Tables` and `_Columns`
  below 32768 (MSIDB-01).
- Template platform tokens are case-sensitive and untrimmed: `X64;1033`,
  `intel;1033`, `arm64;1033` and `x64 ;1033` give 1633. `AMD64;1033` installs
  as x64. `Alpha,x64;1033` installs (first known token), but `x64,Intel;1033`
  gives 1620. `x64;1033,1031` gives 1624: the engine looks for a language
  transform named `1031` (SUM-02).
- Summary code page 65001, 1200, 1201, 32767 and 32768 all open with
  `MsiOpenDatabaseW` but give 1620 in `msiexec`; 932 and 0 install on en-US.
  `MsiSummaryInfoSetPropertyW` accepts any of them without complaint (SUM-04).
- An unbraced or invalid package code (PID 9) gives 87; lower-case hex is
  accepted (SUM-06).
- Same ProductCode with a new package code gives 1638;
  `REINSTALL=ALL REINSTALLMODE=vomus` succeeds (UPG-03).
- `MsiGetFileHashW` returns all zeros for an empty file, not the MD5 of empty
  input; otherwise the MD5 as four little-endian int32 (FILE-02).
- SQL `INSERT` of −32768 into a `SHORT` or −2147483648 into a `LONG` succeeds
  and stores NULL; 40000 fails with 2210 (MSIDB-02).
- A database with code page 0 accepts non-ASCII bytes from the importer and
  returns them as mojibake (MSIDB-08).

Silent-failure cases a producer has to guard against itself:

- A cabinet with wrong DEFLATE history (MSZIP-01) or a payload bit flip with
  checksum 0 (CAB-04) installs with exit 0 and a corrupted file. With a
  checksum, the flip fails with 1603.
- An executable with an empty `File.Version` upgraded with
  `RemoveExistingProducts` at 1401 ends up **deleted**: the new component is
  disallowed against the old versioned file, then the old product is removed.
  At 6601 the old binary stays, as section 8.6 says (FILE-01).
- A deferred script action returning 5 (`msiDoActionStatusFinished`, the
  259 equivalent) ends the install with 0 after `InstallFiles` ran but before
  `RegisterProduct`: the files stay, nothing is registered and nothing rolls
  back (CA-02). The run left one component registration for
  `C:\Program Files\MsiSpecTest\readme.txt` under
  `Installer\UserData\S-1-5-18\Components`, removed by hand afterwards.
- Inline script actions (types 37/38) log "Return value 0" whatever their
  function returns; only syntax errors fail them. Return codes need a
  Binary-stored script (type 6) or a DLL (CA-02).
- An `MsiLockPermissionsEx` deny ACE for `BU` on a file makes the
  uninstall exit 0; it logs `Info 1321 … insufficient privileges … System
  Error 5` and leaves the file behind (SEC-01).

## WiX and msitools one-file packages (ENV-02)

Run on 2026-10-29 on the ENV-01 machine. Both packages install the same
24-byte `hello.txt` per machine into their own folder under
`ProgramFiles64Folder`, with fixed ProductCode, UpgradeCode and component GUID,
from the sources in [`msitest/env02`](msitest/env02):

- **WiX 5.0.2** (`wix --version` 5.0.2+aa65968c): `wix build -arch x64`,
  run by `msitest ENV-02`.
- **msitools wixl 0.106** (PID 18 `msitools 0.106`): `wixl -a x64`, run by
  [`build-wixl.sh`](msitest/env02/build-wixl.sh), which pins the Debian
  trixie package `0.106+repack-1`. Two builds of the same source on
  2026-10-29 had different SHA-256 values, so the log names the hash of the
  package that ran. The package pin and the two hashes come from the build
  setup, not from the logs.

Both tools were used as black boxes; no source of either was read. Both
packages open with `MsiOpenDatabaseW`, answer every `_Tables` query, carry the
same `MsiFileHash` row, embed one single-folder cabinet that `expand.exe`
extracts to the payload, and install and uninstall with exit 0; `hello.txt`
is gone after the uninstall (a check by hand after the run, outside the
logs, found no uninstall entry or folder left). The two agree on the root CLSID,
every table column type they share, the sequence numbers of every action
they share, and summary PIDs 1, 2, 4, 5, 7, 14, 15 and 19 (code page 1252,
`x64;1033`, Page Count 500, Word Count 2, Security 2).

Differences, none of which kept either package from installing (two of
wixl's break spec rules, see below):

| | WiX 5.0.2 | wixl 0.106 |
| --- | --- | --- |
| Container | CFB v4, 4096-byte sectors, 32 KB | CFB v3, 512-byte sectors, 9.5 KB |
| Database code page | 65001 (all-ASCII text) | 0 |
| String refcounts | all equal to the counted references | 51 of 208 differ; the five logged are all too low, e.g. `CostInitialize` stored 1, used 5 |
| Tables | 16 including `_Validation` (77 rows), every one with rows | 33 in `_Tables`; 20 have no rows and no stream; no `_Validation` |
| Cabinet | LZX, `typeCompress` 0x1203 (2¹⁸ window) | MSZIP |
| Upgrade handling | `Upgrade` rows for older and newer versions, a `LaunchCondition` `NOT WIX_DOWNGRADE_DETECTED`, `SecureCustomProperties`, `FindRelatedProducts`, `MigrateFeatureStates`, `RemoveExistingProducts` 1401, without any upgrade element in the source (no upgrade or downgrade was run) | none |
| Other actions | `LaunchConditions`, `CreateFolders`, `RemoveFolders` | none of those |
| `Directory.DefaultDir` | `PFiles64` for `ProgramFiles64Folder`; `iugsytnf\|MsiSpecEnv02Wix` | `.`; `MsiSpecEnv02Wixl` (a 16-character long name without a short part) |
| PID 18 | `WiX Toolset (5.0.2.0)` | `msitools 0.106` |

How the wixl package lines up with earlier findings, each for a normal
install and uninstall:

- Wrong string refcounts are accepted, as finding 3 (MSIDB-05) found for
  reading; section 3 still requires exact ones from a writer, so this is a
  rule wixl breaks, not a producer choice.
- Code page 0 is accepted for all-ASCII text (section 3).
- Tables listed in the catalog without a data stream are accepted (MSIDB-09).
- A package without `_Validation` installs, as section 6.3 states and
  MSIDB-10 confirmed.
- A `DefaultDir` long name without a short part installs, now also in a
  compressed package after CAB-01
  [`uncompressed-longonly-dir`](msitest/results/CAB-01/uncompressed-longonly-dir/log.md);
  sections 6.4 and 8.12 still require an 8.3 short name for every long name.

msi-builder's own choices are unchanged: it keeps exact refcounts and writes
`_Validation` and short names. WiX's 2¹⁸ window fits `medium`, the
v4+ default compression (section 11.6), which section 11 reports as LZX 2¹⁸;
the source set no compression level. Section 13's larger WiX package used
2²¹.
